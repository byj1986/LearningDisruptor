## 120分钟执行顺序

每段完成后再进入下一段；记录预测与实际的差异，数值预期不是已经测得的结果。

### 00～10分钟：准备与预测

- [ ] 核对25天记录，列出未通过项；优先补发布协议、所有权、关闭、数据完整性，不用吞吐量成绩代替正确性。

### 10～30分钟：定向阅读

- [ ] 整理报告骨架：环境与版本、输入载荷、拓扑、容量与策略、结束条件、计时口径、原始结果、限制。为每个结果标来源实验。

### 30～50分钟：最小实验

- [ ] 用完整命令重新构建并运行正常、填充失败、消费失败、过载和关闭超时五类关键场景；记录真实输出及退出原因。

### 50～75分钟：扩展实现

- [ ] 选一组吞吐量和一组延迟配置重跑，检查与历史数据差异；有偏差就解释环境与配置，保留新旧记录。

### 75～105分钟：边界与对照

- [ ] 写一页选型结论：业务所需语义、延迟和CPU预算、测量支持、维护成本及待验证条件；给出一个适用和一个需另选方案的具体情景。

### 105～120分钟：验收与复盘

- [ ] 从根README按顺序走一遍复现步骤，修正失效命令；以能否交给另一位开发者独立复现作为结课标准。

## 验证场景与预期

| 场景 | 输入或条件 | 通过标准或应观察的现象 |
| --- | --- | --- |
| 正确性回归 | 五类关键场景 | 每类结果、计数和退出方式可解释 |
| 性能复现 | 吞吐量与延迟各选一组 | 配置和原始数据齐全，差异有记录 |
| 文档复现 | 从根入口开始 | 版本、构建、运行、数据位置和限制都明确 |

## 不看资料回答

1. 你所说的性能优势是在什么工作量和配置下成立？
2. 如果换成大量异步I/O或更少CPU预算，需要重测什么？
3. 从程序正确到业务可靠，还缺哪些持久化或重试语义？
