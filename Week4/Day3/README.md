## 120分钟执行顺序

每段完成后再进入下一段；记录预测与实际的差异，数值预期不是已经测得的结果。

### 00～10分钟：准备与预测

- [ ] 先画时间线：A申请序号0，B申请序号1；A尚未发布，B已经发布。写下消费者下一个要处理的序号以及你的预测。

### 10～30分钟：定向阅读

- [ ] 阅读CAS申请和可用性标记，将“唯一申请”与“宣布填充完成”分成两条路径，定位寻找最高连续已发布序号的方法。

### 30～50分钟：最小实验

- [ ] 在多生产者配置下，用信号确保A先申请并暂缓发布，再让B申请和发布；容量足够，避免将空间不足混入本实验。

### 50～75分钟：扩展实现

- [ ] 在A仍暂停时，由主控记录已申请序号、各槽位发布状态、消费者已处理数；消费者此时不应越过缺口处理1。

### 75～105分钟：边界与对照

- [ ] 在finally恢复A并完成发布，等待消费0和1。重复3轮，再增加一个后续事件；每个申请都必须有可靠发布清理路径。

### 105～120分钟：验收与复盘

- [ ] 把运行时间线与GetHighestPublishedSequence对应，解释为什么“B已写完”不等于消费者可以跳过A。保存准确源码位置。

## 验证场景与预期

| 场景 | 输入或条件 | 通过标准或应观察的现象 |
| --- | --- | --- |
| 制造缺口 | A取得0不发布，B发布1 | 消费者下一序号为0，不能越过0处理1 |
| 填补缺口 | A随后发布0 | 最终按0、1顺序消费，数据正确 |
| 重复与后续 | 3轮及后续事件 | 无遗留缺口，程序能有界退出 |

## 卡住时先检查

- 不要用随机Sleep保证A/B的关键时序，使用信号并记录取得的实际序号。
- 异常或观察失败也要释放A；只给观察等待加超时，不能遗留永久缺口。
